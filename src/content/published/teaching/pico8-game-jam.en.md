## Moving from exercises to personal work

After the four training sessions, the club held a week-long game jam. It moved the knowledge encountered in follow-along exercises into a game and scope chosen by each creator. I was the main instructor for the preceding course, supported by assistants and other club contributors. The submitted games belong to their respective creators.

This exhibition uses the retained cartridge and source submissions. A file is not necessarily one student, one team or one entirely separate game, so directory counts are not used to infer those totals.

## The retained activity plan

The L03 plan emphasizes a runnable core prototype and an explanation of design tradeoffs. It allows participants to choose a direction rather than require the same kind of game. The documented stages are:

| Stage | Planned emphasis |
| --- | --- |
| Prototype feedback | Demonstrate a runnable core interaction and explain next steps |
| Peer playtesting | Observe another person playing and record problems |
| Revision and polishing | Decide what feedback to address first |
| Wider showcase | Bring the game beyond its developer's computer |

These are retained planning notes. They explain the intended activity design, but do not prove that every stage occurred exactly as scheduled or that every submission received complete playtesting.

## Design questions worth discussing

The plan repeatedly asks for a work that lets a player experience an identifiable idea. Technical work serves that aim, and choices should be explainable: why keep one rule, cut another feature, or wait for player feedback before making a decision?

Reference code and existing assets require source attribution and checking their terms of use. This public teaching account does not repeat the notes' shortcut of treating access to code as unrestricted permission to reuse it. References, modifications and individual contributions should remain distinguishable.

## Turning a playtest into a next step

The original schedule asks creators to record problems during peer play and explain intended revisions. The edited approach separates observed behavior, a hypothesis about its cause and the proposed change. Instead of “the player did not understand,” record where they acted, what they tried and which expected feedback was absent.

The retained material does not include complete scoring, pre/post assessment or all playtest reports. It cannot support a quality assessment of every game or a numerical claim about training effectiveness. The exhibition therefore presents names, files and visible covers without inventing authors or gameplay descriptions.

## Submissions

Cartridges and source files retain their original contents and require an appropriate PICO-8 environment to load. An image cartridge contains game data; displaying its cover does not run the game in the browser. Some internal titles differ from filenames, so original filenames remain available for comparison.

This editorial pass checks file integrity and links. Looking at a cover or source code is not reported as a complete playtest. Return to the [training overview](/teaching/pico8-2026/) for context.
